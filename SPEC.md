# sealctl implementation spec

This spec says how to build sealctl 0.7: the command line tool, the shared Rust core that the phone apps also use, and their tests and packaging. Keys come from 24 words; the phone approves. The Ledger path goes away completely: 0.7 carries no Ledger reader. People on 0.5.0 leave the Ledger with `sealctl unseal --all` from release 0.6.0 (section 24.1), install 0.7 and run `sealctl seal` on each object (section 18).

- Wire formats, derivation, byte layouts and test vectors: [docs/protocol.md](docs/protocol.md). This spec refers to it and does not repeat it.
- The phone apps live in the `app` repository (AGPL-3.0). They depend on `sealctl-core` from a release tag of this repository, with its `uniffi` feature, and generate Swift and Kotlin bindings there.
- The relay is a separate service at `https://relay.sealctl.com`; its public contract is the Relay API section of protocol.md.

| Release | Content |
| --- | --- |
| 0.6.0 | Only `sealctl unseal` (one object, and `--all`) added to the 0.5.0 Ledger code. Nothing else from this spec. Section 24.1 |
| 0.6.x | Fixes to `unseal` only |
| 0.7.0 | Everything else in this spec, including `seal` and `unseal` on the new derivation. First release that needs the phone app. No Ledger code or dependencies |
| 0.7.x | Fixes |

## 1. Terms the CLI uses

Output uses these words and no others for the same things: **Locked**, **Open**, **Waiting**, **One tap**, **Places**, **words**, **phone**, **machine**.

| Term | Meaning on this machine |
| --- | --- |
| Session | The daemon's state for this user: Locked, Open or Waiting |
| Locked | No keys in memory; volumes unmounted |
| Open | Keys in memory; the user and known agents use them without asking |
| Waiting | A request is on the phone. The CLI prints `Waiting for your phone` and gives up after 5 minutes |
| Words fingerprint | 4 characters naming the words that sealed an object (protocol.md) |
| Tag | 4 characters from the pairing key, shown as `#k7m2` |
| Object | Anything sealed with a derived key: the secret store, an own-approval secret, a volume, a backup repository |

### 2.1 sealctl-core

A library crate with `#![forbid(unsafe_code)]` (the generated UniFFI scaffolding is the only exception, behind the `uniffi` feature). It holds everything both sides of the protocol must agree on, so the CLI and the apps can never disagree on a byte.

| Module | Contents |
| --- | --- |
| `words` | Generate 24 words (`getrandom`), validate the checksum, complete a word from its first 4 letters, `Words → Root` |
| `root` | `Root` (32 bytes, `Zeroizing`), `derive(label, len)`, fingerprint, phone identity and box keys, state key |
| `keys` | `ObjectKey` (16 bytes), `check()`, `hex()` for OS tools, `b64u()` for the wire, label validation |
| `ids` | UUID v4 generation and parsing, `.id` file parse and write (`IdFile`) |
| `sealed` | `.sealed` header parse, seal, open (mode 1 and 2), secret name validation |
| `pairing` | QR link build and parse, pairing proof make and check, move proof make and check, tag, hardware hint |
| `wire` | Request, reply, status and message bodies (serde types; field order is the wire order) |
| `request` | Seal a request (machine), open it into a `Request` (phone), open a reply (machine), `rq` |
| `reply` | The phone's replies for every kind: `Decision`, plan signature, rewrap, old words, report |
| `plan` | Plan text, hash and signature, `PlanAssembler`, `PlanApproval` |
| `machine` | `MachineKeys` (pairing seed and box key), tag, hardware hint |
| `channel` | Machine status and machine messages: seal, open, `seq` checks |
| `phone` | `PhoneKeys` (identity seed and box key, 64-byte storage form), words backup item encode and decode, place to allowance numbers |
| `relay_auth` | Canonical string and Ed25519 signing for relay calls; verification for tests |
| `state_blob` | Seal and open of the phone's state blob |
| `tests` | `#[cfg(test)]`: every value of `docs/vectors/v1.json` and `relay-signing.json` (a test fails if any value goes unchecked), RFC vectors, negative cases, property tests, the secret-type check |

Primitives come only from these crates (no hand-written primitives):

| Need | Crate |
| --- | --- |
| SHA-256, HMAC | `sha2`, `hmac` |
| HKDF | `hkdf` |
| PBKDF2 for BIP39 | inside `bip39` (feature `std`, `zeroize`) |
| Ed25519 | `ed25519-dalek` 3 (features `fast`, `zeroize`); `verify_strict` |
| X25519 | `x25519-dalek` 3, through `hpke` (keys are HPKE `X25519HkdfSha256` keys) |
| HPKE (RFC 9180) | `hpke` 0.15 (rust-hpke, features `x25519`, `chacha`, `alloc`), suite `X25519HkdfSha256`, `HkdfSha256`, `ChaCha20Poly1305` |
| AEAD | `chacha20poly1305` 0.11 |
| SHA-256, HMAC, HKDF versions | `sha2` 0.11, `hmac` 0.13, `hkdf` 0.13 (the RustCrypto generation `hpke` 0.15 uses, so there is one copy of each) |
| BIP39 | `bip39` 3 (features `std`, `zeroize`) |
| Randomness | `getrandom` 0.4 (`SysRng`, wrapped in `rand_core` 0.10 `UnwrapErr`) |
| Memory hygiene | `zeroize` (derive, `serde` for reply keys) |
| Encodings | `base64` (URL_SAFE_NO_PAD), `hex`, `serde`, `serde_json`; UUIDs are 16 random bytes with the version bits set, formatted by hand |

### 2.2 UniFFI surface (feature `uniffi`)

Proc-macro annotations only (no UDL), so the app can build `sealctl-core` together with its own crate in UniFFI library mode. **UniFFI 0.32.2**, pinned exactly (`uniffi = "=0.32.2"`) in `crates/sealctl-core/Cargo.toml` and in `Cargo.lock`; the app pins the same version for `uniffi` and `uniffi-bindgen`, and a mismatch fails its build. The crate builds as `lib` and `cdylib`, so `uniffi-bindgen generate --library` can read the library this repository builds. `#![forbid(unsafe_code)]` holds without the feature; with it, `deny(unsafe_code)` (the generated scaffolding is the exception). Secret-holding types are UniFFI objects that zeroise on drop. Object keys (the 16-byte keys) never cross the boundary: the core derives them inside `seal_reply` and its siblings. Errors are one enum `CoreError { UnknownWord { index }, Checksum, Count, BadLink, Expired, NewerVersion, BadProof, BadSignature, BadSealed, Replay, BadLabel, BadPlan, BadKey, WrongDecision, TooLarge, Internal }`; messages never contain key material. `BadKey`: bytes or text that are not a key of the right length; `WrongDecision`: an answer that does not fit the request's kind (keys for a `report`, `Plan` for `open`); `TooLarge`: a body that does not fit its sealed form.

| Export | Returns | Notes |
| --- | --- | --- |
| `Words::generate()` | `Words` | 24 words, OS randomness |
| `Words::parse(list)`, `Words::from_entropy(bytes)` | `Words` | Checksum and word checks |
| `Words.list()`, `Words.entropy()` | 24 strings, 32 bytes | For the protected view and the backup item only |
| `complete_word(prefix)` | Matching BIP39 words | Unique after 4 letters |
| `Root::from_words(words)`, `Root::from_bytes(b)`, `Root.to_bytes()` | `Root` | The seed never leaves Rust |
| `fingerprint(root)` | 4 characters | |
| `PhoneKeys::from_root(root)`, `PhoneKeys::from_bytes(b)`, `.to_bytes()`, `.public_id()`, `.box_public_key()` | `PhoneKeys`; 43-character ids | 64-byte storage form (protocol.md, Phone storage formats) |
| `relay_headers(keys, method, path_and_query, unix_time, body)` | `Sealctl-Key`, `Sealctl-Time`, `Sealctl-Signature` values | Relay API, Signing |
| `PairingOffer::parse(text)` | Machine key, machine box key, name, OS, model, hint, relay origin, version, expiry, tag | Accepts the link or the part after `#`; refuses an expired code (`Expired`). The pairing code stays inside the object |
| `pairing_proof(keys, offer)` | 86-character proof | Needs the phone keys only |
| `machine_tag(machine_key)` | 4 characters | |
| `open_request(keys, relay_machine_key, id, sealed)` | `Request` | HPKE, machine signature, time window (`Expired`), version, plan rules (`BadPlan`), at most 4,096 characters (`BadSealed`). Answered ids are the app's to keep (protocol.md, Request) |
| `Request` | `kind`, `ctx` (agent, repository id and name, command, cwd, user, subject, names), `items` (purpose, id, path or URL, size, words fingerprint, key check), `uses`, `old` (retired fingerprint), `status` (for `report`), `handback` (for `report`), `plan` (items, `all`, hash, part), `level()` (the confirmation level the phone applies: the kind's level or `lvl`, whichever is higher), `has_match`, `rq`, `version` | The number match is held inside `Request`; it never crosses the boundary |
| `Request.match_choices()`, `Request.check_match(pick)` | Three numbers (`u32`) in display order, the same on every call; `bool` | The right number and two random others; only an offered number can be right, and a wrong pick is final for that request (protocol.md, Number match) |
| `PlanAssembler::new()`, `.add(request)` | Complete plan or `None` | Collects the parts of a plan sent in several `unseal` requests and checks `h` (`CoreError::BadPlan`); the whole plan is then attached to the request that completed it, which the `Plan` decision answers. A one-part plan is complete when opened |
| `seal_plan_part_reply(keys, request)` | Sealed reply | `{"ok": true, "part": i}` for each part but the last |
| `plan_approval(request, not_before)` | `PlanApproval { machine, hash, not_before, keys }` | What the app keeps after a `Plan` answer, for `seal_plan_keys_reply` |
| `seal_reply(root_or_none, keys, request, decision)` | Sealed reply | `decision`: `Deny`, `Refuse { err }`, `Once { place }`, `Session { place }`, `Remember { place }`, `Plan { place, not_before }`; `place` is `Trusted`, `Other` or `NoLocation`. Needs the root only when the request asks for keys; without it such an approval is answered `phone_locked`. `Once`, `Session` and `Remember` fit `open`, `keys`, `agent` and `own`; `Plan` fits `unseal`; `Deny` and `Refuse` fit every kind (`WrongDecision` otherwise). An approval of a level 3 request without a right number pick is answered `no_match`. `Plan` signs the plan hash (protocol.md, Plan and plan signature) and hands out only keys named by plan items (`outside_plan` otherwise), as many as fit, with `more`. Items whose `w` is not the current fingerprint, or whose `c` does not match, get `wrong_key` |
| `seal_reply_with_retired(root_or_none, keys, request, decision, retired)` | Sealed reply | As `seal_reply`; items sealed with words in `retired` (`{fingerprint, retired: "YYYY-MM-DD"}`) get `retired_words` |
| `seal_plan_keys_reply(root, keys, request, approval)` | Sealed reply | Answers a later `unseal` request of an approved plan: keys named by plan items only (`outside_plan`), inside the 30 minutes after `not_before` (`plan_expired`, also before it); another machine or hash is `BadPlan` |
| `seal_rewrap_reply(old_root, new_root, keys, request)` | Sealed reply | Old and new key per item, `grant: once`; an item's `c` is checked against the key of the words its `w` names |
| `seal_old_words_reply(old_root, root, keys, request)` | Sealed reply | Derives only the listed objects' keys |
| `seal_report_reply(keys, request, ack, messages)` | Sealed reply | Fallback channel |
| `key_change_proof(old_keys, new_keys, machine_key)` | 128-character move proof | protocol.md, Phone key change |
| `licence_move_proof(new_keys, old_public_id)` | Base64url signature | Relay API, Moving the licence |
| `state_seal(root, plaintext)`, `state_open(root, blob)` | Blob as base64url (as the relay's `blob` field), plaintext | |
| `seal_machine_message(keys, machine_key, machine_box_key, message)` | Sealed message | `MachineMessage { version, time, seq, kind }`, `kind` one of `Lock`, `Answers`, `Ack`, `Notice` |
| `open_machine_status(keys, machine_key, sealed)` | `MachineStatus` | |
| `backup_item_encode(words, fingerprint, created)`, `backup_item_decode(bytes)` | 45 bytes; fields | |
| `core_version()`, `protocol_version()` | `"0.7.0"`, `"1"` | |

The CLI uses the same functions from Rust (machine side: `seal_request`, which also returns the number match when the body has `match`; `open_reply`; `plan_text` and `verify_plan_signature`; `seal_status`, `open_message`, `.id` and `.sealed` handling), which are not exported to the apps.

The app repository builds the XCFramework and Android libraries; this repository's `bindings.yml` workflow only proves that bindings generate and a Swift and a Kotlin smoke test call `fingerprint` and `open_request` on the vectors.

The binary is not code-signed by a stable identity, so a keychain item would ask for permission after every `brew upgrade`; the key only identifies the machine and opens nothing by itself. On start, the CLI refuses to use `machine.json` if it is readable by group or others, and says `chmod 600 <path>`.

## 5. Output rules

### 5.1 Streams

- **stdout** carries the result: a value someone asked for, a list, JSON. Nothing else.
- **stderr** carries progress, `Waiting for your phone`, notes and errors.
- No emoji (0.5.0 used them). Plain words; one line per fact.
- Colour only when the stream is a terminal and `NO_COLOR` is unset. Colour never carries meaning by itself.

### 5.2 Who is reading

| Context | Detected by | Rules |
| --- | --- | --- |
| A person at a terminal | stdin and stderr are terminals, no agent, no `CI` | Prompts allowed; the ask may show (section 19) |
| An AI agent | Agent environment variables (`CLAUDECODE`, `CODEX_THREAD_ID`, `GEMINI_CLI`, `QWEN_CODE`, `COPILOT_AGENT_SESSION_ID`, `OPENCODE`, `CURSOR_AGENT`, `AI_AGENT`, as in 0.5.0) or `SEALCTL_AGENT=1` | No prompts; values never printed; `sealctl run` masks; refusals use exit 8; no ask, no price, no request to pass anything on |
| A pipe, CI or a service | stdout or stderr not a terminal, or `CI` set | No prompts (a command that needs one fails with exit 8 and says which flag to use); masking in `sealctl run`; no ask |

`Waiting for your phone` is printed once on stderr in every context, because agents read it too. When nobody watches a terminal (the SSH agent, git signing, the backup schedule) and no agent is detected, the daemon also shows a desktop notification: "sealctl: waiting for your phone" (`osascript` on macOS, `notify-send` on Linux, silently skipped if missing).

### 5.3 JSON

Commands with `--json` print exactly one JSON object on stdout, UTF-8, keys in camelCase, times in RFC 3339 with offset, sizes in bytes, durations in seconds. Errors still go to stderr as text, with the exit code; `--json` adds nothing to stdout on error. Fields are only added, never renamed, within 0.x.

### 5.4 Exit codes

| Code | Meaning |
| --- | --- |
| 0 | Done |
| 1 | Error not listed below |
| 2 | Usage error (bad arguments, conflicting relay) |
| 3 | Not paired, or this machine was unpaired |
| 4 | Declined on the phone |
| 5 | No answer from the phone in time |
| 6 | Relay unreachable or relay error (5xx, unexpected answer) |
| 7 | Relay limit reached (`429`) |
| 8 | Refused: inside an AI agent, or needs a terminal |
| 9 | Not found: secret, volume, backup, object |
| 10 | Wrong words or wrong key: check mismatch, retired words, words fingerprint mismatch |
| 11 | Volume busy |
| 12 | Clock off by more than 5 minutes |
| 13 | Stopped part way: `seal` or `unseal` did some steps and kept its journal; run it again with `--resume` |

`sealctl run` exits with the program's own code (128 + signal number when killed by a signal); its own failures before the program starts use the codes above.

### 5.5 Error messages

Every error is one line on stderr starting with `sealctl: `, then at most one line saying what to do. Relay errors end with the status page. Exact texts:

| Case | Text |
| --- | --- |
| Not paired | `sealctl: This machine is not paired. Run: sealctl pair` |
| Unpaired on the phone | `sealctl: This machine was unpaired on your phone. Run: sealctl pair` |
| Declined | `sealctl: Declined on your phone.` |
| No answer | `sealctl: No answer from your phone in 5 minutes.` |
| Relay unreachable | `sealctl: Cannot reach the relay (relay.sealctl.com): <reason>. Status: https://sealctl.com/status` |
| Relay 5xx | `sealctl: The relay failed (<code>). Status: https://sealctl.com/status` |
| 429 phone | `sealctl: Your phone reached the relay's daily limit of 5,000 requests. It resets at 00:00 UTC.` |
| 429 network or key | `sealctl: Too many requests from this network. Try again in <n> s.` |
| Clock | `sealctl: This computer's clock is <n> minutes off. Set the time automatically and try again.` (uses the relay's `time` when given) |
| Agent refusal | `sealctl: Not inside an AI agent: <what>. Use sealctl run -- <command>.` |
| Retired words | `sealctl: Sealed with words 7Hq3, retired 2028-03-02. Type them on the phone to move this object to your current words.` |
| Other words | `sealctl: Sealed with words 7Hq3; your phone has words qHWf.` |
| Busy volume | `sealctl: Volume safe is busy: node (pid 4211) has files open.` |
| Wrong number picked (`no_match`) | `sealctl: The number picked on your phone was not 59. Nothing was changed.` |
| Held after a wrong number (`held`) | `sealctl: Your phone holds sensitive requests from this machine for an hour after a wrong number. Try again after 11:42.` |
| Not near (`not_near`) | `sealctl: Your phone could not tell it is near this machine. Run this at the machine's terminal and pick the number on your phone.` |
| No biometrics (`no_biometrics`) | `sealctl: Your phone needs Face ID or a fingerprint for this. Fix that on the phone, or use your card: <command> --words` |
| Cancelled during the delay | `sealctl: Cancelled from your phone.` or `sealctl: Cancelled from dev@box.example.com.` |

## 6. The session daemon

One daemon per user holds the session: the keys, the timers, the relay connections and the SSH agent socket. Every command that needs a key talks to it.

### 6.1 Starting and stopping

| Situation | How the daemon runs |
| --- | --- |
| Paired desktop or laptop | Login service installed by `sealctl pair`: launchd `com.sealctl.daemon` (`RunAtLoad`, `KeepAlive`) or systemd user unit `sealctl.service` (`Restart=on-failure`). Runs `sealctl daemon` |
| Service missing (containers, dev boxes without a user systemd) | The CLI starts `sealctl daemon --spawned` detached (`setsid`, stdio to `/dev/null`). It exits after 10 minutes Locked with no client |
| `SEALCTL_NO_DAEMON=1` (CI runners) | No daemon. Each command asks the phone itself; keys live as long as that process. No Open session, no SSH agent |

- The CLI and the daemon are the same binary. Every socket request carries the CLI version; on a mismatch the daemon answers, then exits, and the service manager (or the next CLI call) starts the new binary. `brew upgrade` therefore needs no step.
- 0.7 never changes or removes anything 0.5.0 made. If 0.5.0 objects or services remain (`~/.config/sealctl/keys/`, `~/.config/sealctl/volumes/*.toml` without `words`, `~/.local/share/sealctl/secrets/**/*.gpg`, `~/.ssh/sealctl_<name>` files encrypted with a passphrase, services `io.github.oleksiyp.sealctl.*`), `pair`, `status` and `doctor` print, on stderr: `sealctl: Found objects from sealctl 0.5 (Ledger). Hand them back first with sealctl 0.6: sealctl unseal --all. See https://sealctl.com/docs/from-ledger`. `pair` then exits 2 unless `--force`. Using such an object gives the same line and exit 10.

### 6.2 Socket

`$XDG_STATE_HOME/sealctl/daemon.sock`, mode 0600 in a 0700 directory. The daemon checks the peer's uid (`getpeereid` on macOS, `SO_PEERCRED` on Linux) and closes any connection from another uid. Messages are JSON lines: `{"v": 1, "cli": "0.7.0", "op": ..., ...}` answered by `{"ok": true, ...}` or `{"ok": false, "error": <code>, "message": <text>}`, where `<code>` maps to the exit codes in 5.4. Values travel over this socket only in `values` and `own` answers.

| Op | Does |
| --- | --- |
| `status` | Session state, timers, objects, last error |
| `open` | Open the session (or join a pending open) |
| `lock` | Lock now, with `force` and `noBackup` flags |
| `values` | Secret values for names, with the caller's context (agent, repo, cmd, cwd). Opens the session or asks the phone as needed |
| `own` | Values of `--own-approval` secrets for one command |
| `keys` | Volume and backup keys for the CLI's volume and backup commands |
| `store` | Write, rename or delete a secret (the daemon holds the store key) |
| `events` | Stream of `waiting`, `answered`, `locked`, `notice` events, so the CLI prints `Waiting for your phone` once |
| `pending` | Delayed level 3 actions known from `notice` messages and the relay's `delayed` notes, for `status` and `cancel` |
| `rewrap`, `migrate` | Section 16 |

### 6.3 States

```text
          need a key                      approved (grant: session)
 Locked ─────────────► Waiting ─────────────────────────────────────► Open
   ▲                    │  declined, no answer (5 min), Ctrl-C            │
   │                    └──────────────► Locked                          │
   │   idle allowance used, hard stop, sealctl lock, lock message,        │
   └───── unpaired, daemon exit ◄──────────────────────────────────────────┘
```

- **Waiting** is a sub-state: the daemon is Locked or Open and a request is on the phone. There is one pending `open` at a time; other callers that need the same session join it. A caller whose need the pending request does not cover (another agent use, an own-approval secret) gets its own request after the pending one is answered.
- `grant: once` hands the keys to the waiting command only; the session stays Locked.
- On Open the daemon holds the store key, the keys of auto volumes it mounted, and the backup keys of configured backups (all asked for in the same `open`).

### 6.4 Timers and credit

- **Minute worked:** a wall-clock minute in which the input idle time dropped below 60 seconds at any 15-second sample, or in which a key was used. Input idle time: macOS `HIDIdleTime` from the `IOHIDSystem` IOKit service; Linux the logind session `IdleSinceHint` over D-Bus. Where neither works (dev boxes, CI), only uses count.
- **Idle allowance:** `min(cap, base + rate × minutes worked today)` with `cap`, `base`, `rate` from the last `open` reply (protocol.md, Reply body).
- **Lock on idle:** when `now − last work moment ≥ idle allowance`. Time asleep counts as idle (wall clock). Screen lock and sleep do not lock by themselves.
- **Hard stop:** 02:00 local time or 14 hours after the first `open` granted today, whichever is first. It locks and resets the credit (minutes worked) to 0.
- **Credit** survives locks and daemon restarts until the hard stop; it is kept in `session.json` with the first-approval time.
- **Own-approval keys** are wiped when the command that asked exits (the daemon watches the client connection).
- The daemon samples every 15 seconds. It detects sleep by comparing the wall clock with the monotonic clock at each tick, and then checks the idle allowance and hard stop at once.

### 6.5 Locking

On any lock the daemon, in this order:

1. wipes the store key, decrypted SSH keys, own-approval keys and the per-agent session allowances;
2. runs on-lock backups with the backup keys it still holds (skipped with `--no-backup`, after a lock message `words`, and on unpairing), at most 15 minutes in total;
3. unmounts volumes; a busy volume is reported with the process holding it (`lsof -F pcn <mountpoint>` on macOS, `fuser -vm` on Linux) and retried every 60 seconds; `sealctl lock --force` force-unmounts;
4. wipes the backup and volume keys;
5. sends a status (`locked`, with any busy volumes) and closes the machine socket.

### 6.6 The machine channel

While Open, the daemon keeps the phone informed and listens for locks (protocol.md, Machine status and messages):

- When the relay offers the machine channel (planned in protocol.md; specified in the relay spec), it opens the machine socket and sends status with `PUT .../status`. A `404 not_found` on the socket upgrade means this relay does not offer it yet; the daemon then uses the fallback below and tries the socket again after 6 hours.
- Until then it keeps one `report` request waiting (ttl 300, renewed at most once per 60 seconds) and applies `ack` and `msgs` from the reply.
- Usage log entries wait in `usage.jsonl` until a status that carries them is acknowledged. The log holds names, agents, repositories and masked commands, never values.
- A `lock` message locks at once (reason shown by `sealctl status`: "Locked from your phone" or "Locked: your phone left the place"). An `answers` message replaces `answers.json` (used by `sealctl rules`).
- A `notice` message (protocol.md, Message body) or a relay `delayed` note on the machine socket announces a level 3 action. The daemon keeps it in memory, shows it in `sealctl status`, and shows a desktop notification (5.2) whether or not an agent is running:
  - pending: `sealctl: your phone approved leaving sealctl on dev@mbp.example.com away from a trusted place. It takes effect at 11:00. Not you? Run: sealctl cancel`. The relay's own note, without the phone's details, reads `sealctl: a sensitive action was approved on your phone. It takes effect at 11:00. Not you? Run: sealctl cancel`;
  - cancelled: `sealctl: cancelled from your phone: leaving sealctl on dev@mbp.example.com`;
  - done with a report: `sealctl: dev@mbp.example.com handed back 9 objects (macOS Keychain). 0 failed.`
- A Locked machine has no machine socket, so it learns of a pending action at its next relay call; `sealctl status` asks the relay (`GET .../delayed`, 2-second timeout) every time it runs.

### 6.7 Process hardening

At start the daemon sets `RLIMIT_CORE` to 0, on Linux `prctl(PR_SET_DUMPABLE, 0)`, on macOS `ptrace(PT_DENY_ATTACH)`. Key buffers are `mlock`ed where the OS allows (failure is logged once at `info`, not fatal). The daemon never writes keys or values to disk.

## 7. Relay client

- One origin per machine, recorded at pairing (`relay` in `machine.json`). `SEALCTL_RELAY` or `--relay` sets it for `pair`; a paired machine refuses a different one (exit 2) so a typo cannot split a machine from its phone.
- Every call is signed as in the Relay API (`sealctl-core::relay_auth`) with the pairing key. TLS through rustls with the platform verifier; HTTP/1.1 or HTTP/2; 10-second timeout per call; `HTTPS_PROXY` and `NO_PROXY` honoured.
- Retries: network errors and `5xx` are retried at 1, 2 and 4 seconds, then the command fails with exit 6. `429` is not retried: exit 7 with the reset time. `401 clock_skew` fails with exit 12 and the offset from `time`.
- Wait sockets send `ping` every 30 seconds (planned on the relay; harmless before) and keep their own 300-second timer, since the relay has no expiry timer.
- A `403 forbidden` or a wait closed with `unpaired` or `moved` makes the daemon look itself up (`GET /v1/machines/{machine}`): a move proof moves it to the new phone key (protocol.md); `404 not_paired` locks and marks the machine unpaired (exit 3 for the caller).
- Licence answers are cached for 1 hour in `licence.json`. `sealctl status` refreshes a stale cache with a 2-second timeout and shows the cached value when the relay is slow.
- The client logs method, path, status and duration at `debug`; never headers, bodies or sealed strings.

## 8. Pairing

### 8.1 `sealctl pair`

```text
sealctl pair [--name <user@host>] [--force] [--relay <origin>]
```

1. If this machine is paired: on a terminal, ask `This machine is paired as dev@mbp.example.com #k7m2. Pair again? This replaces its pairing. [y/N]`; without a terminal, exit 2 unless `--force`.
2. Make a new pairing key, machine box key and 16-byte pairing code. Collect the name (`$USER@` plus the full hostname: `hostname -f` on Linux, `scutil --get HostName` or else `LocalHostName.local` on macOS; `--name` overrides), OS (`sw_vers` or `/etc/os-release`), model (`sysctl hw.model`, `/sys/class/dmi/id/product_name`), and hint (protocol.md).
3. Print to stderr, on a terminal, the QR code (UTF-8 half blocks, quiet zone 2) and below it:

   ```text
   Scan with the sealctl app on your phone. Or open this link on the phone:
   https://sealctl.com/p#v=1&m=…&e=1795252200
   Waiting for your phone (10 min)
   ```

   Without a terminal (remote sessions, Claude on the web), print only the link on stdout and the waiting line on stderr.

   Pairing is confirmation level 2 on the phone: biometrics, and the app's own camera scanning the code as proof that the person sees this machine. A link opened on the phone takes the user to the scanner. So the printed link, opened in a browser on the computer the user sits at, shows the QR code: the website's `/p` page draws it from the fragment, which never reaches the server.
4. Poll `GET /v1/machines/{machine}` every 2 seconds until the code expires. Check the proof (protocol.md). A wrong proof: exit 1 with `This pairing did not come from your phone. Run sealctl pair again.`
5. Save `machine.json`, delete the old pairing key if any, install the daemon service, create the store if none exists (the first `open` asks for the new store key), and print on stdout `Paired: dev@mbp.example.com #k7m2`.
6. On the first pairing of this user, print on stderr (terminal only): `Free to use. If it earns its place, $5.99 once keeps the relay running: sealctl buy`.

Exit 5 when the code expires unpaired. The machine gate (`402` on the phone's side) is the phone's to show; the CLI just times out.

### 8.2 Duplicates, tags and labels

- The phone handles a pairing under a name already paired (same hint: Replace; different hint: "Same machine?"; "Pair as new" for clones). The machine sees no difference. A machine replaced on the phone gets `404 not_paired` on its next call and shows `This machine was unpaired on your phone. Run: sealctl pair`.
- `sealctl status` always prints the tag, so the terminal and the phone list can be matched. A nickname set on the phone is not known to the machine.

### 8.3 `sealctl unpair`

`DELETE /v1/phones/{phone}/machines/{machine}` signed by the machine, then lock, delete `machine.json` and the daemon service. Objects stay; they open again after pairing with the same phone or words. Asks for confirmation on a terminal; `--yes` otherwise.

## 9. Approvals as the CLI sees them

| Situation | Request | What the user sees in the terminal |
| --- | --- | --- |
| Locked; a person runs `sealctl run`, `secret get`, `volume open`, `ssh`, `git commit -S` | `open` with the needed items, subject and names | `Waiting for your phone`, then the command runs |
| Locked; an agent runs `sealctl run` | `open` with `uses` for that agent, repository and names | Same; one tap covers both |
| Open; a person uses any secret | None | Nothing |
| Open; an agent uses a secret it has not used in this repository in this session | `agent` | `Waiting for your phone` unless the phone remembers the answer |
| Open; a secret set with `--own-approval` | `own`, every time | `Waiting for your phone` |
| Open; a new volume, backup or own-approval secret is created, or a manual volume is opened | `keys` | Usually nothing (automatic while the phone is unlocked) |
| Any; the phone key changed | `rewrap`, `lvl` 2 | `Moving to your new words…` on stderr if a command waits on it. Level 2: biometrics on the phone, and `near`, since the daemon has no terminal for a number (16.1) |
| Any; an object sealed with retired words is used | `old_words` | The retired-words message (5.5), exit 10; the phone asks for the words |
| `sealctl seal` of a new object | `keys` | `Waiting for your phone` unless automatic (level 1: nothing changes hands) |
| `sealctl seal` of an existing object | `keys` with `ctx.subject` `{"k": "machine", "n": "seal"}`, `lvl` 2, `match` | `Waiting for your phone. On your phone, pick 47 if it asks.` Level 2 on the phone |

| `sealctl unseal --all` | `unseal` with the plan, `lvl` 3, `match` | `Waiting for your phone. On your phone, pick 59.` Level 3, with the delay away from a trusted place (18.9). With `--words`, no request |

- Repository: `git rev-parse --show-toplevel` from the working directory; id and name per protocol.md (`ctx.repo`). Outside git, `repo` is `null` and answers are kept per folder path.
- A person is never asked inside an Open session. An agent is identified only by the environment variables in 5.2; that is a guard against mistakes, not against malware (threat model).
- Allowed agent uses are kept in daemon memory until the session locks; `remember` answers also go to `answers.json` when the phone sends them.
- A file in the repository never grants anything: `.sealctl.toml` only names which secrets a command gets.
- **Confirmation levels** (protocol.md, Confirmation levels): the CLI sets `lvl` to the level of what it is about to do and `match: true` whenever a person at a terminal is shown the number. It prints the number on stderr, once, on the `Waiting for your phone` line. The phone decides the level; the CLI's `lvl` can only raise it.

### 10.3 `sealctl run`

```text
sealctl run [-e NAME=secret]... [--no-project] -- <command> [args...]
```

- Mappings: `[env]` of the nearest `.sealctl.toml` (searched upwards from the working directory), then `[command."<words>"]` sections whose words are a prefix of the command line (longest prefix wins per variable), then `-e`, which wins.

  ```toml
  [env]
  OPENAI_API_KEY = "shop/openai-api-key"

  [command."npm run deploy"]
  DEPLOY_TOKEN = "shop/deploy-token"
  ```

- stderr first lists what the program gets: `sealctl: OPENAI_API_KEY ← shop/openai-api-key` (names only), because a cloned repository can contain a `.sealctl.toml`.
- Values come from the daemon (`values`, plus `own` for own-approval secrets), then the program starts with them in its environment only.
- Masking as in 0.5.0: inside an agent or when stdout or stderr is not a terminal, the program's output passes through the masker (raw, base64, URL-encoded forms) and values print as `****`. Otherwise `exec` replaces sealctl.
- Never prints the ask, a price, or any text meant for an agent to pass on.
- One use log entry per run (names, agent, repository, masked command).

## 12. Secret store

- The store format is protocol.md, Store format. The daemon holds the store key while Open and does every seal and open.
- A new store: `uuid v4` id, folder `~/.local/share/sealctl/store/<store-id>/`, the key from the first `open` (item without `w`/`c`), `.id` written last.
- `--own-approval`: a mode 2 file. Its key is asked with a `keys` request at creation and an `own` request at every use; it lives in daemon memory until that command exits. Its check goes into the `.id` file's `own` map.
- Listing, removing and the names in `SessionStart` read the folder only; they need no key.
- A store folder synced between machines works on all of them: the key depends on the store id and the words only. Two machines writing the same file at once: last rename wins; `secret ls` shows `modified` so the user can see it.
- 0.5.0 `secrets/*.gpg` files are never read by 0.7 (section 6.1). `sealctl unseal` in 0.6.0 hands them back first.

## 13. Volumes

| Kind | Default on | Created with | Id | Opened with | Words marker while locked |
| --- | --- | --- | --- | --- | --- |
| `apfs` | macOS | `diskutil apfs addVolume <container> APFS <name> -stdinpassphrase -nomount` with a throwaway passphrase, then `changePassphrase` to the derived one (as 0.5.0) | Volume UUID | `diskutil apfs unlockVolume <uuid> -stdinpassphrase` | `diskutil apfs setPassphraseHint <disk> -user disk -hint "sealctl <fp>"` |
| `sparsebundle` | macOS, portable | `hdiutil create -type SPARSEBUNDLE -fs APFS -encryption AES-256 -stdinpass` | Generated UUID in `<bundle>/sealctl.id` | `hdiutil attach -stdinpass` | `sealctl.id` |

## 14. Backups

- `backup init` makes a repository id (UUID); the repository URL is `<base URL>/<repo-id>`. Credentials the backend needs (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `B2_ACCOUNT_ID`, `B2_ACCOUNT_KEY`, …, as 0.5.0's list) are asked with a hidden prompt or taken from `-e`, and stored as secrets `backup/<name>/<VAR>`. The backup key comes from a `keys` request.
- restic gets the password on a pipe: `--password-file /dev/fd/3` (and `--from-password-file /dev/fd/4` where two are needed). Never an argument, never `RESTIC_PASSWORD`.
- After `restic init`, sealctl adds a key with `--user sealctl --host sealctl-<fp>` and removes the key `init` made, so the words fingerprint is readable from `keys/`.
- The 0.5.0 cache of password and credentials inside the volume (`<mount>/.sealctl/repo.toml`) is removed: backup keys and credentials are held by the daemon while Open.
- Schedule and on-lock backups run only while the daemon holds the keys (Open, or during step 2 of a lock).
- Retention as 0.5.0 (7 daily, 4 weekly, 12 monthly, `forget --prune` at most weekly).

## 15. Inventory and .id files

- `inventory.json` lists every object this machine created, opened or found: kind, name, purpose, id, words, check, path or URL, size, created, last use, last seen.
- Every key item in a request carries `o` (kind, path or URL, size), so the phone's inventory fills itself. Status messages carry the full list (`inv`) when it changes.
- `seal` adds the object; `unseal` removes it and sends the changed `inv`, so the phone's inventory shows it as handed back rather than not seen.
- `sealctl inventory` prints it: `store  0f8c6d2e…  qHWf  ~/.local/share/sealctl/store/0f8c6d2e…  12 KB  used 2 min ago`. `--json`: `{"objects": [...]}`.
- `.id` files and markers: protocol.md, Ids and .id files. Reading markers never needs a key: `diskutil info`, `diskutil apfs listUsers` (hint), `cryptsetup luksDump --dump-json-metadata`, `sealctl.id`, the restic `keys/` objects (local folder, or S3 `GET`).

## 16. Changing words and `sealctl migrate`

### 16.1 Rewrap, by itself

When the words change, the phone moves each machine to its new key (protocol.md, Phone key change). The daemon notices on its next relay call (`403`, or a wait closed with `unpaired` or `moved`), checks the move proof, and then, without any command:

1. sends a `rewrap` request listing every object in `inventory.json` whose words are the old fingerprint (several requests if they do not fit);
2. for each item, with the old and new keys from the reply:

| Object | Rewrap |
| --- | --- |
| Secret store | Every `.sealed` file re-encrypted with the new file key (mode 1) or new own-approval key (mode 2), file by file with atomic renames; the `.id` file replaced last with the new words and check. Files still showing the old words in their header are rewrapped on the next run |
| APFS volume | `diskutil apfs changePassphrase <uuid> -user disk` with old and new passphrases on stdin; new hint |
| Sparse bundle | `hdiutil chpass -oldstdinpass -newstdinpass`; new `sealctl.id` |
| LUKS | `cryptsetup luksAddKey --key-file /dev/fd/3 <file> /dev/fd/4`, then `luksRemoveKey` with the old key, then the token replaced |
| Restic repository | `restic key add --user sealctl --host sealctl-<new fp>` with old and new passwords on fds, then `restic key remove <old key id>`; on S3-compatible storage with versioning, the old versions of that `keys/` object are deleted (`ListObjectVersions`, `DeleteObjects`); where that is impossible, `sealctl migrate` says `Old key file versions remain in <bucket>; delete them in the provider's console.` |

3. updates `inventory.json`, sends a status, and logs `Rewrapped 12 objects to words 4kPz` at `info`.

Rewrap is confirmation level 2 on the phone: biometrics per request, and proximity. The daemon has no terminal, so it relies on the relay's `near`; a `not_near` answer leaves the objects on the old words, retried at the next daemon start, and `sealctl migrate --depth rewrap` at the machine's terminal sends the same request with a number (`On your phone, pick 23 if it asks.`).

Rewrap needs each object reachable: an unmounted APFS volume can be rewrapped locked; a LUKS file and a sparse bundle need only the file; a restic repository needs its credentials (from the store). Objects that fail stay on the old words and are retried at every daemon start and listed by `sealctl migrate`.

### 16.2 `sealctl migrate`

Run by a person on each machine that holds volumes or backups to re-encrypt.

```text
$ sealctl migrate
Moving from words 7Hq3 to 4kPz. Measured: disk 410 MB/s, upload 9 MB/s, download 40 MB/s.

  object                    size    rewrap   re-encrypt
  secret store (7 files)    12 KB   done     -
  volume safe (APFS)        38 GB   done     about 4 min, needs 38 GB free (210 GB free)
  backup safe-backup (R2)   52 GB   done     about 1 h 35 min to 2 h 10 min
  ssh key ed25519           1 KB    done     -
  not on this machine: volume work (LUKS) on dev@box.example.com, last seen 3 days ago

Re-encrypt volume safe and backup safe-backup now? It keeps running if you close the terminal. [y/N]
```

- The table goes to stdout, the question to stderr. Without a terminal it prints the table and exits 0; `--yes` starts the job without asking.
- The CLI sends a `report` with the `migrate` estimates so the phone's plan shows them. The `not on this machine` line needs the phone's inventory, which no message carries yet (open question 27.6); until then it is left out.
- `--depth rewrap` retries rewrap for objects that failed; `--depth re-encrypt` (the default) proposes re-encryption for volumes and backups.
- `--status [--json]`: job state per object, percent, rate, time left, paused reason. `--pause`, `--resume`, `--cancel` (cancel stops after the current step; nothing half-done is deleted).
- Estimates: volumes `used size × 2 / disk speed` (read and write); backups `size / download + size / upload`, shown as a range of ×0.8 to ×1.25. Disk speed: write and read back 256 MiB in a temporary file on the target disk with the cache bypassed (`F_NOCACHE`, `O_DIRECT`). Network: put and get one 32 MiB object under the repository base (`.sealctl-speed-<random>`, deleted after); folder repositories use disk speed.

### 16.3 The re-encryption job

A launchd job `com.sealctl.migrate` or systemd user service `sealctl-migrate.service` running `sealctl migrate --run-job` (hidden), restarted on failure, removed when done. State in `migrate.json`; every step is idempotent and resumes where it stopped.

| Object | Steps |
| --- | --- |
| APFS volume | Check free space ≥ used size (else stop with the needed size). Unmount; add a new APFS volume in the same container; get its key with a `keys` request; mount the old one read-only at a private mountpoint; copy with `ditto` (a resumed copy runs `ditto` again); compare file count and total size, and SHA-256 of 1% of files picked at random; delete the old volume; rename the new one; update the volume config with the new id. The volume cannot be used during the job; `sealctl volume open` says so |
| Sparse bundle | Same, with a new bundle beside the old one, then the old bundle deleted and the new one renamed |
| LUKS | Close the volume; `sudo cryptsetup reencrypt --resilience checksum <file>` with the key on a file descriptor (offline, resumable by cryptsetup itself) |
| Restic repository | New repository id; `restic init --from-repo <old> --copy-chunker-params` with both passwords on fds; `restic copy --from-repo <old>` (skips snapshots already copied); `restic check` on the new one; then delete the old repository's objects (folder: remove the folder; S3-compatible: delete all objects and versions under the prefix); update the backup config. Other restic backends (sftp, rest, rclone): stop before deleting and print what to delete |

- Paused while on battery below 20% (macOS `pmset -g batt`; Linux `/sys/class/power_supply/BAT*/capacity` and `status`), resumed at 25% or on mains power.
- Progress goes to `sealctl migrate --status`, `sealctl status` and the phone (status `migrate`).
- The job needs the session Open only to get the new object keys; it asks once at the start, with one `keys` request for all new ids.

### 16.4 `--scan`

`sealctl migrate --scan [PATH...]` (default: home, `/Volumes`, mounted disks) finds objects by their markers: `*.id` files with `"sealctl": 1`, `sealctl.id` in sparse bundles, LUKS files (magic `LUKS\xba\xbe` with a `sealctl` token), APFS volumes (`diskutil apfs list -plist`, hint `sealctl <fp>`), and backup configs. It adds them to `inventory.json`, prints them, and sends a `report` with the `inv` field. After a restore from paper alone, the phone's plan cannot check completeness; the CLI says `Your phone has no inventory from before; only what machines report is listed.` when the phone's reply says so.

### 16.5 Retired words

An object whose words are neither the phone's current words (`w` in any reply) nor rewrapped gives the retired-words message when used (exit 10). `sealctl migrate` lists such objects and, on `y`, sends one `old_words` request with `old` set; the phone asks the user to type those words and replies with old and new keys; the machine rewraps as in 16.1.

### 16.6 Objects from 0.5.0

0.7 has no Ledger reader. An object sealed by 0.5.0 is handed back with `sealctl unseal` from release 0.6.0 (section 24.1), then taken over with `sealctl seal` (section 18). Section 6.1 says what 0.7 prints when it finds one.

## 17. `sealctl recover`

Opens an object with the 24 words alone: no phone, no relay, no pairing, no config.

```text
sealctl recover <store folder | .sealed file | sparse bundle | LUKS file | APFS volume UUID | restic repository URL>
                [--out <dir> | --name <secret> [--show]] [-- <restic arguments>]
```

1. Refused inside an AI agent and without a terminal on stdin (exit 8): the words must be typed by a person.
2. Reads the object's marker for its kind, id and words fingerprint.
3. Asks for the 24 words one at a time with no echo (`Word 1 of 24:`); the first four letters are enough; an unknown prefix asks again; a failed checksum asks again from the start, three tries.
4. Computes the root, compares its fingerprint with the marker: on a mismatch, `These words have fingerprint qHWf; this object was sealed with words 7Hq3.` and exit 10.
5. Derives the object's key, checks it against the marker's check, then:

| Target | Result |
| --- | --- |
| Store folder | `--out <dir>`: each secret written to `<dir>/<name>` (dir 0700, files 0600), own-approval secrets included; `--name <n>`: one value to stdout (pipe, or a terminal with `--show`) |
| `.sealed` file | Same as `--name` |
| Volume | Unlocked and mounted at its default mountpoint; prints the mountpoint and how to eject (`diskutil eject`, `umount` and `cryptsetup close`) |
| Restic repository | Runs `restic <arguments>` (default `snapshots`) with the password on a file descriptor and credentials from the environment, asking for missing ones without echo |

The words, seed and root are zeroised before the command exits. `sealctl recover` writes nothing else and contacts no network except the restic backend.

## 18. Seal and unseal

`sealctl seal` takes over something the user already has: a volume, a restic backup, an SSH key or a secret. `sealctl unseal` hands one object back under the user's own password; `sealctl unseal --all` hands back everything on the machine, then removes sealctl's settings, services and AI hooks. Together with `recover`, this is what stands behind "if we disappear, your keys don't": leaving never needs the phone, the relay or sealctl's company.

The same rules, journal and password stores serve both directions. Release 0.6.0 ships the `unseal` half on the 0.5.0 Ledger code (section 24.1); 0.7 ships both on the new derivation, described here.

### 18.1 Rules

| Rule | How |
| --- | --- |
| Plan first | Nothing changes before the plan (18.5) is shown and confirmed: `y` for one object, the typed word `unseal` (or `seal`) for `--all` and `--from`. `--dry-run` shows the plan and exits 0 |
| Check before removing | Each object is opened with the new key or password before the old one is removed. Where the OS swaps a passphrase in one step (APFS, sparse bundles), the check runs at once after the swap; if it fails, the swap is reversed with the old passphrase, which still works in that case |
| A journal for resuming | Every step is written to the run's journal (18.4) before and after it runs. `--resume` continues; each step first checks whether it is already done on the object itself |
| Every edited file copied | Before its first edit, each file (`~/.ssh/config`, shell rc files, agent settings, git config files) is copied into the run folder with its mode |
| No phone, relay or Ledger needed | `unseal` gets keys from the phone when it answers, with `unseal` requests bound to the confirmed plan, at confirmation level 2 (objects) or 3 (`--all`) (18.9). With `--words`, or when the phone or relay cannot be reached, it asks for the 24 words as `recover` does; no level, number or delay applies then |
| A person at a terminal | stdin and stderr must be terminals; refused inside an AI agent with exit 8. `--all` has no `--yes` |
| No values shown | Values and passwords go only to the chosen store and are read back to check them by SHA-256 in memory. The only exception is the store `show`, chosen by the user, which writes each new password once to `/dev/tty` |
| Nothing deleted that could be needed | Data is never deleted. Replaced files and the old store folder move to the run folder's `kept/`, still encrypted, and the final message says where |

### 18.2 Commands

```text

sealctl unseal --all [--skip <kind>/<name>]... [--keep-store]
sealctl unseal --resume

Password and secret stores (both commands):
  [--to keychain|op|bw|show] [--secrets-to keychain|op|bw|env] [--env-file F]
  [--op-vault V] [--bw-folder F] [--type-passwords] [--no-ssh-passphrase]

```

Tools without such a setting are listed as having none | `ai status` shows nothing installed; every edited file still parses | Optional deny rules that need no sealctl |
| Services | Daemon, backup schedule and migration units removed; the daemon stopped | `launchctl print` or `systemctl --user status` finds none | |
| Local state | `~/.config/sealctl`, `~/.local/state/sealctl`, `~/.ssh/sealctl_*.pub` removed; `~/.local/share/sealctl` moved to `kept/` | The folders are gone | |
| Pairing | `DELETE /v1/phones/{phone}/machines/{machine}`, signed by the machine. Without network: skipped, and the output says `Unpair dev@mbp.example.com on your phone.` | `GET /v1/machines/{machine}` answers `404 not_paired` | |
| The program | Never removed by sealctl. The last line names the command for how it was installed: `brew uninstall sealctl/tap/sealctl`, `sudo apt remove sealctl`, `sudo dnf remove sealctl`, `sudo pacman -R sealctl`, `nix profile remove sealctl`, or the binary's path | | |

`unseal --all` runs in this order: secrets, volumes and backups (each backup before the volume that holds its source), SSH keys, git, AI integrations, services, local state, pairing; the program last, by the user. A single `unseal <object>` does that object's steps only and leaves sealctl installed and paired.

### 18.3 Where passwords and secrets go

New passwords (volumes, backups, SSH keys) go to one store, chosen once per run: `--to`, or a question on the terminal listing only the stores present. Secrets and backup storage credentials go to `--secrets-to`, which defaults to the same store.

| Store | Writes | Reads back | Needs |
| --- | --- | --- | --- |
| `keychain` (default) | macOS Keychain or the Linux Secret Service (GNOME Keyring, KeePassXC) through the `keyring` crate: service `sealctl-unsealed`, account `<kind>/<name>` (for example `volume/safe`, `secret/shop/openai-api-key`, `backup/safe-backup/AWS_SECRET_ACCESS_KEY`), label `sealctl: volume safe` | The same API | macOS; on Linux a running Secret Service, else this store is not offered |
| `op` | 1Password: `op item create` with a JSON item template on stdin; category Password (secrets: API Credential); title as the label; tag `sealctl`; vault `--op-vault` or the account's default | `op read op://<vault>/<item id>/password` into memory | `op` signed in |
| `bw` | Bitwarden: `bw encode` and `bw create item`, both reading stdin; folder `--bw-folder` | `bw get password <item id>` into memory | `bw` unlocked (`BW_SESSION` set) |
| `show` | Opt-in. Each new password written once to `/dev/tty`: `New passphrase for volume safe: …` then `Write it down. Type its last 4 characters to go on:` | The 4 characters typed | A terminal |
| `env` (secrets only) | `--env-file` (default `~/sealctl-secrets.env`), mode 0600, `NAME=value`, the name from the secret name upper-cased with `/`, `-`, `.` as `_`; two secrets with the same variable name stop the plan | Parsed back with the dotenv parser | A warning in the plan: `This file holds your keys in plain text, where AI agents can read them. Move them to a password manager, then delete it.` |

- Values reach `op`, `bw` and the OS keychain through stdin or the native API, never an argument or an environment variable.
- New passwords are generated: 32 characters of `a-z0-9` in groups of four joined by `-` (about 165 bits), from OS randomness. `--type-passwords` asks for each one instead, twice, at least 12 characters.
- The item's notes say what it opens and how: `APFS volume safe (UUID …). Open with: diskutil apfs unlockVolume <uuid>`, or the restic repository URL.

**Hand-back list.** `unseal` writes `handback.json` in the run folder. It holds no password or value: one entry per object with its kind, name, path, URL or UUID, and where its password went.

```json
{
  "sealctl": 1,
  "kind": "handback",
  "created": "2026-11-21T10:31:07+01:00",
  "machine": "dev@mbp.example.com",
  "from": "0.6.0",
  "objects": [
    {"kind": "volume", "name": "safe", "volume": "apfs", "uuid": "<uuid>", "password": {"store": "keychain", "service": "sealctl-unsealed", "account": "volume/safe"}},
    {"kind": "backup", "name": "safe", "url": "<restic URL>", "password": {"store": "keychain", "account": "backup/safe/password"}, "credentials": [{"var": "AWS_ACCESS_KEY_ID", "store": "keychain", "account": "backup/safe/AWS_ACCESS_KEY_ID"}]},
    {"kind": "ssh", "name": "ed25519", "path": "~/.ssh/ed25519", "password": {"store": "op", "vault": "Private", "item": "<item id>"}},
    {"kind": "secret", "name": "shop/openai-api-key", "value": {"store": "env", "file": "~/sealctl-secrets.env", "var": "SHOP_OPENAI_API_KEY"}}
  ]
}
```

`sealctl seal --from <file>` reads it and proposes every object in it.

### 18.4 Run folder and journal

Each `seal` or `unseal` run (other than `--dry-run`) makes `~/.sealctl-unseal/<run>/`, mode 0700, where `<run>` is the local start time, `2026-11-21T10-12-03`. It sits outside sealctl's folders so that `unseal --all` can remove those and still finish.

| File | Content |
| --- | --- |
| `plan.json` | The plan as confirmed: objects, steps, chosen stores |
| `journal.jsonl` | One line per step event |
| `files/<path under $HOME>` | The copy of every file before its first edit, with its mode |
| `kept/` | Objects moved instead of deleted: the old store folder, old key files |
| `handback.json` | 18.3 |
| `run.lock` | Held with `flock` while the run is active; a second run exits 2 |
| `done` | Written last |

Journal line:

```json
{"v": 1, "t": "2026-11-21T10:14:02+01:00", "n": 7, "step": "volume:safe:change", "state": "done", "note": "passphrase changed; verify passed"}
```

`state` is `start`, `done`, `failed` or `skipped`. `note` never holds a value, a password, or a path inside the secret store. Lines are appended and `fsync`ed.

- `--resume` takes the newest run without `done`. A plain `unseal --all` that finds one asks `Resume the run from 10:12? [Y/n]`.
- For each step not `done`, the step's check runs first against the object (does the new password already open it? is sealctl's key already gone?), so a step interrupted after it took effect is recorded, not repeated.
- Ctrl-C lets the current OS call finish, writes the journal line, and exits 13.
- The final message names the run folder and says it can be deleted once everything opens with the new passwords.

### 18.6 Failure and resume

- A failed step stops the run. Steps before it stay done. The output names the step, says which key or password opens the object now (from the journal), and ends with `Run sealctl unseal --resume after fixing this.` Exit 13.
- `--skip <kind>/<name>` leaves one object out, for example a backup whose storage is offline. With a skipped object, `--all` keeps whatever that object still needs (services, local state, pairing) and exits 13, saying so.
- A volume that cannot be mounted to remove its `.sealctl/` folder, or that stays busy, is reported with the process holding it (exit 11 at the end); its passphrase change still runs.
- Never: deleting data, removing the only key that opens an object, or writing a value anywhere but the chosen store.

### 18.7 Exit codes

0 done; 2 usage, or another run active; 4, 5, 6, 7 from the phone or relay when keys come from the phone (then `--words` works); 4 also for a wrong number, `held`, `no_biometrics` and a delay cancelled from the phone or another machine; 8 inside an agent or without a terminal; 9 no such object; 10 the derived key does not open the object (other words; `.id` check mismatch); 11 a volume busy; 13 stopped part way or with skipped objects.

### 18.9 Confirmation on the phone

`seal` and `unseal` ask the phone at the confirmation levels of protocol.md: level 2 for `seal` of an existing object and `unseal <object>`, level 3 for `unseal --all` and any plan with a pairing step. With `--words` none of this applies: no request, no number, no delay. Release 0.6.0 (24.1) keeps its own gate: a real terminal, the typed `unseal`, the Ledger PIN once.

**`unseal --all`, step by step.**

1. The plan is built, shown and confirmed with the typed `unseal` (18.5), as before.
2. The CLI turns the plan into plan items (protocol.md, Plan and plan signature): one per row of the plan, with the key each step needs, and computes `h`. It sends `unseal` with `lvl` 3, `match: true`, `plan` and the keys of the first items. A plan over the body size goes in parts; only the last part carries `match`.
3. It prints, on stderr:

   ```text
   Waiting for your phone. On your phone, pick 59.
   ```

4. Then, by answer:

   | Answer | CLI does |
   | --- | --- |
   | Reply with `grant: "plan"` and `nb` already passed | Checks `sig` with the phone key against its own `h`, the request id and `nb`; writes `h`, `nb`, `sig` into `plan.json`; starts the run |
   | Relay `delayed` note | Keeps the one-time key in memory and waits, below |
   | `no_match`, `held`, `no_biometrics`, declined | The texts of 5.5; exit 4; nothing changed |
   | No answer in 5 minutes | Exit 5, as any request |

   While delayed:

   ```text
   Approved on your phone, away from a trusted place: it starts at 11:00.
   Your phone and every paired machine can cancel it until then.
   Starts in 59 min. Ctrl-C stops waiting; running it again needs a new approval.
   Or use your card now: sealctl unseal --all --words
   ```

   The `Starts in` line is rewritten in place each minute on a terminal (one new line every 10 minutes otherwise). The CLI reads `GET /v1/phones/{phone}/delayed/{id}` every 60 seconds and at `releaseAt`, by wall clock, so a laptop that slept catches up. `state: "cancelled"` ends with `Cancelled from your phone.` (or the machine's name), exit 4. A reply fetched early by a faulty relay is not used before `nb`.
5. **Inside the plan only.** Before each step, the CLI checks that the step's plan line is in the signed plan, and before using a key, that a plan item names it. Anything else is a bug: the run stops, exit 1, the journal says which step. Keys that did not fit in the first reply come from further `unseal` requests with `plan: {"h"}`, which the phone answers without asking, up to 30 minutes after `nb`.
6. **Resume.** `--resume` within 30 minutes of `nb` continues with the same approval. Later, it shows the remaining plan, asks for the typed `unseal` again, and sends it as a new level 3 request: new number, new delay away from a trusted place.
7. **Report.** Before the pairing step, the CLI sends a `report` with `handback`: each plan item, where its password or value went, and done, failed or skipped. The phone shows it and tells the other paired machines. If the report cannot be sent, the run goes on and the end text adds `Your phone did not get the report.`

**`unseal <object>` and `seal`.** The same request at level 2: no delay, and the number is used by the phone only when it cannot tell it is near (`On your phone, pick 47 if it asks.`). `seal` sends `keys` with `ctx.subject` `{"k": "machine", "n": "seal"}`, `lvl` 2 and `match`.

**Cancelling from another machine.** `sealctl cancel` (10.1) on any paired machine, or Cancel on the phone, cancels a pending delayed action. The CLI waiting on it learns at its next read.

## 19. Licence

Everything is free. The relay says whether to ask; the CLI decides when and where.

### 19.1 The ask

Shown as one line on stderr after the command finishes, when all of these hold:

- the command is `status`, `pair`, `secret ls` or `migrate`, typed by a person: stdin and stderr are terminals, no agent detected, `CI` unset;
- the cached licence (at most 1 hour old, refreshed by `status`) says `ask: true`;
- the last ask was 7 or more days ago (`licence.json`).

Text, with `daysUsed` from the relay:

```text
You've used sealctl on 41 days. It's $5.99 once: sealctl buy
```

Never in `sealctl run` output, pipes, CI, hooks or anything an agent reads; never a countdown; never on the phone. `sealctl status` always shows `Unpaid · sealctl buy` while unpaid (that line is a fact, not the ask), and `--json` carries `"licence": "unpaid"`. The monthly summary line shows paid or not.

### 19.2 `sealctl buy`

Needs a pairing (the licence is attached to the phone key). Refused inside an AI agent (exit 8). Without `--seats` or `--code` it needs a terminal.

```text
$ sealctl buy
Who pays?
  1  Me             card, opens checkout
  2  My company     invoice with VAT ID, opens checkout
  3  Someone else   copies a payment link to send
Choose 1, 2 or 3:
```

| Choice | Does |
| --- | --- |
| 1 | `POST /v1/phones/{phone}/checkout` with `{"seats": 1}`, opens the link (`open` or `xdg-open`), prints it, then checks the licence every 5 seconds for up to 15 minutes: `Waiting for the payment. Ctrl-C stops waiting; sealctl status shows it later.` Then `Paid. Thank you.` |
| 2 | Same checkout (Paddle asks for the company and VAT ID), and copies a message for the team chat: `Could we get sealctl for me? It keeps API keys away from AI agents. $5.99 once: <link>` |
| 3 | Copies the link and prints it: `Link copied. Anyone can pay it; sealctl status shows Paid afterwards.` No wait |

- `--seats N` (2 to 1,000): checkout for N seats; after payment prints `Seat code ACME-7KQ2 (10 seats, 1 used by you). Each developer runs: sealctl buy --code ACME-7KQ2`.
- `--code CODE`: `POST /v1/phones/{phone}/claim`: `Paid with a seat from ACME-7KQ2. 8 seats left.` Errors map: `unknown_code` → exit 9 `No such code.`; `no_seats_left` → exit 1 `That code has no seats left.`; `already_paid` → exit 0 `This phone is already paid.`
- `already_paid` on checkout for one seat: exit 0 `Already paid. Thank you.`
- `payments_not_configured` or `payments_unavailable`: exit 6 with the status link.
- A licence never blocks keys, `recover`, the words or any command. The machine gate (off at launch) is applied by the relay at pairing only.

## 20. Security requirements

| Area | Requirement |
| --- | --- |
| Key types | Every key and value is a type that zeroises on drop (`Zeroizing`, `SecretBox`). No `Debug`, `Display` or `Serialize` on secret types; `#[derive(Debug)]` on a struct holding one is a compile error (checked by a test that greps the crate and by `clippy::disallowed_types` config) |
| Copies | Values are not copied into `String` unless an API needs it; such copies are `Zeroizing<String>`. No `format!` of a value |
| Memory | Daemon: no core dumps, `PR_SET_DUMPABLE 0` on Linux, `PT_DENY_ATTACH` on macOS, `mlock` best effort |
| Files | No key or value ever written to disk except by `recover --out` and `secret get` into a pipe the user made. Section 3 modes; refuse to run with a group- or world-readable `machine.json` |
| Processes | Values to OS tools only through stdin or a file descriptor pipe; never arguments or environment variables, except the program's own environment in `sealctl run`, which is the point |
| Logs | No value, key, seed, word, sealed string or request body in any log, error, panic message or `--verbose` output. Panics use `panic = "unwind"` with a hook that prints only the location |
| Sockets | 0600 sockets in 0700 directories; peer uid checked |
| Clipboard | Copies clear after 30 seconds if the clipboard still holds the value |
| Network | TLS only (except loopback test relays); certificate checks never disabled; relay errors never echo request bodies |
| Words | Typed only into `sealctl recover`, and into `seal` and `unseal` with `--words`; read without echo; never accepted as an argument, from stdin when it is not a terminal, or from the environment |
| Levels | `lvl` never lower than the action's level (18.9); `match: true` only when the number is printed to a terminal a person reads; the number is never logged, never in `--json`, never in the journal; a plan reply is used only after its `sig`, `h` and `nb` check, and only inside the plan |
| Replies | A reply is used only after HPKE open, signature check with the paired phone key, `rq` check and key check against the `.id` file |
| Agents | `secret get`, `recover`, `seal`, `unseal`, the credential helpers and `buy` refuse inside agents; masking cannot be turned off inside an agent |
| Hand-back | `seal` and `unseal` give values and passwords only to the chosen store (stdin or native API), check them by hash, and write none to the journal, the run folder or the terminal (except the opt-in `show` store) |

## 21. Engineering safeguards

Most of this code is written with AI coding agents. A security tool cannot ship unreviewed crypto, so these rules are enforced by the repository, not by good intentions.

- **Human-reviewed paths.** `.github/CODEOWNERS` requires the maintainer's review on: `crates/sealctl-core/**`, `docs/protocol.md`, `docs/vectors/**`, `crates/sealctl/src/{relay,daemon,store,run,guard,recover,pair}/**`, `crates/sealctl/src/ai/**`, `crates/sealctl/src/migrate/**`, `crates/sealctl/src/seal/**`, `Cargo.toml`, `Cargo.lock`, `deny.toml`, `supply-chain/**`, `.github/**`. Branch protection on `main` requires that review and green CI. Each such pull request says in its description which parts a person read line by line.
- **Established crates only** for primitives: `sha2`, `hmac`, `hkdf`, `ed25519-dalek`, `x25519-dalek`, `hpke`, `chacha20poly1305`, `bip39`, `getrandom`, `zeroize`, `secrecy`. No hand-written HKDF, HPKE, AEAD, base64 or constant-time compare (`subtle::ConstantTimeEq`). A CI grep fails on new `unsafe`, on `rand::thread_rng` in core, and on new dependencies in `sealctl-core` without a reviewed `supply-chain` entry.
- **Vectors.** CI runs RFC vectors (RFC 5869 HKDF, RFC 8032 Ed25519, RFC 7748 X25519, RFC 9180 A.2, RFC 8439, BIP39 English) through the chosen crates, plus every value in `docs/vectors/v1.json` and `relay-signing.json`. CI also re-runs `node docs/vectors/generate.mjs` and fails if the output differs from the committed JSON, so the protocol, the script and the code cannot drift.
- **Cross-implementation tests.** The relay signing vectors are verified in this repository with WebCrypto (`node -e` with `crypto.subtle`, as the relay does) and the relay's own tests load the same file. The app's Swift and Kotlin tests load `v1.json`.
- **Fuzzing.** `cargo-fuzz` targets for every parser: QR link (`PairingOffer::parse`), `.sealed` header and file, `.id` file, request body, reply body, status and message bodies, the sealed-string decoders, relay JSON answers and WebSocket frames, `.sealctl.toml`, dotenv, the git credential protocol input, the daemon socket JSON lines. `fuzz.yml` runs each for 2 minutes on every pull request touching a parser and 1 hour nightly; crashes become regression tests.
- **Leak tests.** Integration tests run every command with a known canary value in the store and fail if the canary (raw, base64, URL-encoded, hex) appears in stdout (except where printing it is the command's job), stderr, `daemon.log`, panic output or any file under the config and state folders. One test forces a panic inside a function holding a key and checks the output.
- **Secret types.** A test walks `sealctl-core`'s public types and fails if a secret-holding type implements `Debug`, `Display`, `Clone` (where not needed) or `Serialize`.
- **Supply chain.** `cargo-deny` (licences, advisories, duplicate versions, banned crates such as `openssl`), `cargo-vet` with imports from Mozilla, Google and the Bytecode Alliance audits; unaudited crates need an exemption in `supply-chain/config.toml` reviewed by the maintainer. Dependencies are kept minimal: no new crate for anything a few lines of safe code can do, except crypto.
- **Reproducible releases.** Pinned toolchain (`rust-toolchain.toml`), `--locked`, `SOURCE_DATE_EPOCH` from the tag, `--remap-path-prefix`, fixed `codegen-units = 1`. CI builds each release artifact twice on separate runners and compares hashes for the Linux tarballs. Every artifact gets a GitHub build attestation (`actions/attest-build-provenance`); `SHA256SUMS` is attested too.
- **Disclosure log.** `SECURITY-CHANGELOG.md` lists every security-relevant change and fix with the version and date, separate from `CHANGELOG.md`.
- **External review.** An external review of `sealctl-core`, protocol.md and the daemon's key handling before 1.0; findings and fixes published in `SECURITY-CHANGELOG.md`.
- **Public explanation.** protocol.md's derivation, pairing and request/reply sections name every key, label and step, so the page sealctl.com/crypto can draw them. Changes to those sections are reviewed for that too.

### 24.1 0.6.0: unseal on the Ledger version

**Scope.** Version 0.6.0 is the 0.5.0 code in `crates/sealctl/src` with one command added: `sealctl unseal`, for one object or `--all`. Nothing else from this spec goes in: no phone, relay, new derivation, `seal`, or output changes to other commands. It follows section 18's rules (18.1), stores (18.3), run folder and journal (18.4), failure handling (18.6) and exit codes (18.7), with the differences below. Its job: hand every 0.5.0 object back under the user's own passwords, so that the user can install 0.7 and `seal` each one, or leave.

**Keys.** From the Ledger through the existing session agent (`agent::oracle`), so the PIN is asked once. The confirmation levels of 18.9 do not apply to 0.6.0: there is no phone, and its gate stays a real terminal, the typed `unseal` and the PIN. With `--words`, from the Ledger's 24 words through `recover::SeedOracle`, checked against the certificate exactly as `recover` does today, after this warning: `These words also guard anything else on your Ledger. Type them only if the Ledger is lost or broken.` Nothing reaches a phone or relay.

**Commands.**

```text
sealctl unseal --all [--to keychain|op|bw|show] [--secrets-to keychain|op|bw|env] [--env-file F]
                     [--op-vault V] [--bw-folder F] [--type-passwords] [--no-ssh-passphrase]
                     [--keep-env-rules | --drop-env-rules] [--skip <kind>/<name>]... [--words] [--dry-run]
sealctl unseal secrets | secret <name> | volume <name> | backup <volume> | ssh <name> | git | ai [TOOL...]   (same flags)
sealctl unseal --resume
sealctl askpass        (hidden: SSH_ASKPASS helper, reads one passphrase from the pipe named by SEALCTL_ASKPASS_FD)
```

## 27. Open questions

1. **Machine channel on the relay.** Agreed with the relay and still marked planned in protocol.md. Until it ships, the `report` fallback works but costs up to 288 relay calls a day per Open machine, and each `report` may trigger a push, since the relay pushes for every request and cannot tell kinds apart. Once the channel ships, the fallback is used only against an older relay.
2. **Backup keys for the whole session.** The design says "machine memory during a backup". Scheduled and on-lock backups need the key without a tap, so the daemon holds it while Open. Alternative: ask the phone per backup with a `keys` request, automatic while the phone is unlocked.
3. **Pairing key in a file.** The design allows the OS keychain or a 0600 file. The file avoids keychain prompts after each upgrade of an unsigned binary. Revisit if releases get a stable code-signing identity.
4. **Agent first-use tap** (design open decision): kept as specified.
5. **APFS re-encryption without free space** (design open decision): the job stops and says how much space is needed; rewrap stays done.
6. **Other machines in the `migrate` table** need the phone to send its inventory to a machine. Add an `inventory` message type, or drop that line.
7. **Keyboardless machines** (design open decision): only sealctl uses count as work there, as specified.
8. **APFS hint readability.** Whether `diskutil apfs listUsers` shows the passphrase hint must be checked on macOS 15 and 26; if not, `migrate --scan` reads the words of a locked APFS volume only from `inventory.json`.
9. **CI runners and Claude on the web.** `SEALCTL_NO_DAEMON=1` and the printed pairing link make them work, but each ephemeral runner would pair anew. A pairing that outlives the runner (a long-lived key in the CI secret store) is not designed.
10. **Fingerprint case.** The 4-character words fingerprint is base58 and case-sensitive, as in the design's examples; handwriting may confuse `k`/`K`. A lower-case base32 form would be easier to copy.
11. **"nothing written to disk"** in the monthly summary is a statement sealctl can only make about itself.
12. **Reading keys from 1Password, Vault, Doppler** (design open decision): not in 0.7. `seal secret --from-op` and `--from-bw` read one value once; they are not a live source.
13. **APFS and sparse bundles swap their passphrase in one step.** There is no second slot to add first, so the check runs right after the swap and a failed check swaps back (18.1). Confirm on macOS 15 and 26 that `diskutil apfs unlockVolume -verify` works on a mounted volume and on a locked one.
14. **The SSH passphrase in the macOS keychain.** `ssh-add --apple-use-keychain` stores it in the login keychain only through `ssh-add` itself, so `unseal` feeds it through `SSH_ASKPASS`. If Apple's `ssh-add` ignores `SSH_ASKPASS_REQUIRE=force` on some macOS version, the user types the passphrase once, read from the store's item.
15. **Linux without a Secret Service** (servers, minimal desktops): the `keychain` store is not offered; the plan asks for `op`, `bw` or `show`. Is `show` acceptable as the only option there?
16. **Homebrew users who upgrade before unsealing.** `brew upgrade` takes a 0.5.0 user straight to 0.7. The tap keeps `sealctl@0.6` and 0.7 prints how to use it (6.1). Should 0.7.0 be held back on the tap for some weeks after 0.6.0, so that most users unseal first?
17. **Remote machines and proximity.** Level 2 counts the number match as proximity, so `unseal <object>` works on a dev box over SSH. Rewrap from the daemon has no terminal and needs `near`; a dev box or CI runner is never near, so its rewrap waits for `sealctl migrate --depth rewrap` run there by hand. Acceptable, or exempt rewrap during a change of words the user just started on the phone?
18. **Pending notices on Locked machines.** A Locked machine has no machine socket and hears of a delayed action only at its next relay call or `sealctl status`. Keeping the machine socket open while Locked would announce at once, at the cost of pings from every machine all day (relay spec).
